# 关于如何写好提示词

## 一 核心黄金法则：CRISPE框架

|**要素**|**含义**|**示例**|
|---|---|---|
|**C**apacity (角色)|让 AI 扮演特定的专家|“你是一位拥有 10 年经验的 Java 首席架构师...”|
|**R**equest (任务)|明确具体要做什么|“请帮我重构这段 PostgreSQL 空间查询的 SQL...”|
|**I**nput (输入)|提供的原始数据或背景|“这是当前的 SQL 语句以及执行计划：`[贴入代码]`...”|
|**S**timuli (限制/提示)|设定边界条件和防错机制|“必须考虑索引失效问题，禁止使用不必要的子查询...”|
|**P**rocess (步骤)|规定思考或执行的顺序|“第一步分析瓶颈，第二步给出优化 SQL，第三步解释原因...”|
|**E**xit (输出要求)|规定返回的格式和语气|“请用 Markdown 表格对比优化前后的性能，语气要专业简练...”|

## 二、 进阶编写技巧（拉开差距的关键）

#### 1、给出示例（Few-Shot Prompting ⭐️）

#### 2. 让 AI “一步一步想”（Chain-of-Thought）

对于复杂的逻辑推理、数学计算、代码架构设计，在 Prompt 的结尾加上一句：**“请一步一步思考（Let's think step by step）”**。 这会强制大模型开启逻辑链条，降低由于“嘴快”导致的幻觉和逻辑错误。

#### 3. 使用清晰的标签分隔符

当你的输入包含很多背景资料、代码段或参考文章时，用 `---`、`###` 或 `xml 标签`（如 `<context></context>`）把它们隔开，防止 AI 分不清哪部分是指令，哪部分是数据。

## 三、 一个实用的 Prompt 通用模板

Markdown  
# Role  
你是一位专业的 [职位/身份]，在 [某个领域] 有着深厚的背景。  
​  
# Task  
我需要你帮我 [具体任务]，目标的受众是 [受众群体]。  
​  
# Context  
背景信息如下：  
- [背景 1]  
- [背景 2]  
​  
# Constraints  
请务必遵守以下规则：  
1. 必须 [准则 1，例如：保持客观中立]  
2. 绝对不能 [红线 1，例如：使用过多的技术术语]  
3. 如果遇到不确定或不知道的信息，直接回答“不知道”，不要编造。  
​  
# Output Format  
请用以下格式输出：  
- 核心结论（加粗）  
- 详细拆解（使用无序列表）

## 四、日常调教 AI 的思维误区（避坑）

**别玩“猜心游戏”**：不要写“帮我写个报告”。AI 不知道你要写 500 字还是 5000 字，不知道是给老板看还是给客户看。**明确永远大于含糊。**

**多用“要什么”，少用“不要什么”**：负向提示（如“不要太死板”）的干扰效果往往不如正向提示（如“请使用幽默、接地气的口吻”）有效。

**Prompt 是迭代出来的**：不要指望一次性写出完美的 Prompt。先给一个基础指令，看到 AI 的反馈后，针对它回答得不好的地方**针对性地增加限制条件**（比如：“很好，但请把第三点写得更深入一些”），这才是最自然的 AI 协同状态。

## 五、如何写一个产出skill的prompt

# Role  
你是一位资深的 Devops 专家和高级工具链架构师。  
​  
# Task  
请帮我编写一个用于 CI 门禁的自动化合规检查 Skill。  
具体业务逻辑是：[比如：检查向 ai-coding-hotel 仓库提交的 MR 中，是否包含了 AGENTS.md 文件，如果没有则拦截]  
​  
# Technical Stack  
- 语言：[Go / Python / Shell 等]  
- 依赖：[如：需要调用 GitLab API 或是本地 Git 命令]  
​  
# Constraints & Standards  
1. 性能优化：必须支持增量检查，只对当前 MR 变更的文件进行处理，避免全量扫描。  
2. 健壮性：对所有外部命令或 API 调用必须做好超时控制（Timeout）和异常捕获，防止脚本僵死。  
3. 日志规范：如果校验不通过，输出必须包含 [错误原因]、[问题文件/行号]、[明确的修复建议]。  
4. 退出码：校验成功请执行 exit 0；校验不通过（业务拦截）请执行 exit 1 并输出结构化提示。  
​  
# Output Format  
请给出完整的、生产环境可用的代码，并在关键逻辑处加上中文注释。
